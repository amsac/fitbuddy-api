FITBUDDY AUTHENTICATION REQUIREMENTS
====================================

Document Purpose
----------------
This document defines the authentication requirements for the FITBUDDY application.

It is intended to be used as an implementation reference for Codex or another coding agent.

The current application already has:
- Spring Boot backend
- PostgreSQL database
- React / React Native clients
- User entity
- Workout templates
- Workout sessions
- Exercise logs
- Set logs
- Workout history

Authentication was previously skipped and the clients used hardcoded userId = 1.

This document replaces that approach with JWT-based authentication.


============================================================
1. AUTHENTICATION SCOPE - VERSION 1
============================================================

Authentication V1 should support:

1. User registration
2. User login
3. JWT access token generation
4. JWT validation for protected APIs
5. Getting the currently authenticated user
6. BCrypt password hashing
7. TRAINER and STUDENT roles
8. Both TRAINER and STUDENT can create workout templates for now
9. User-specific APIs must derive the user from JWT instead of trusting userId sent by the frontend
10. Architecture must remain ready for a future Forgot Password / Reset Password feature

Do NOT implement the following in V1:
- Refresh tokens
- OAuth
- Google login
- Apple login
- Facebook login
- Email verification
- Forgot password implementation
- Reset password implementation
- Role-specific authorization rules
- Admin role
- Token blacklist
- Server-side JWT logout
- Multi-factor authentication

Logout in V1 simply means deleting the JWT token on the frontend.


============================================================
2. AUTHENTICATION MODEL
============================================================

Use:

- Spring Security
- JWT access token
- BCryptPasswordEncoder
- Email as the primary login identifier
- Stateless authentication

High-level flow:

Client
  -> POST /auth/login
  -> Spring Security authenticates email/password
  -> Backend creates JWT
  -> Client stores JWT
  -> Client sends JWT in Authorization header
  -> JwtAuthenticationFilter validates token
  -> Spring SecurityContext contains authenticated user
  -> Controllers/services derive current user from authentication


Authorization header format:

Authorization: Bearer <jwt-token>


IMPORTANT SECURITY RULE:

The frontend must NOT be trusted to tell the backend which user is performing an action.

Avoid user-specific request fields such as:

{
  "userId": 1
}

when the backend can determine the user from the JWT.


============================================================
3. USER ENTITY
============================================================

Existing User entity concept:

User
- id
- name
- email
- role
- createdAt

Add:

- password

Recommended structure:

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(nullable = false)
    private String password;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private Role role;

    private LocalDateTime createdAt;
}


Role enum:

public enum Role {
    TRAINER,
    STUDENT
}


IMPORTANT:
- Never store plain text passwords.
- Password values must always be BCrypt hashes.
- Email should be stored normalized, preferably lowercase.
- Email should remain unique.


============================================================
4. FUTURE FORGOT PASSWORD READINESS
============================================================

Forgot Password is NOT part of Auth V1.

However, authentication should be designed so it can be added later without redesigning login.

Use email as the login identifier.

Future endpoints can be:

POST /auth/forgot-password
POST /auth/reset-password


Future flow:

User submits email
  -> backend generates secure short-lived reset token
  -> reset token is emailed to user
  -> user submits reset token + new password
  -> backend verifies token
  -> password is replaced with a new BCrypt hash


Do NOT add password reset token fields directly to User.

Later create a separate entity such as:

PasswordResetToken
- id
- user
- tokenHash
- expiresAt
- usedAt
- createdAt

This entity is NOT required for V1.

============================================================
8. REGISTER API
============================================================

Endpoint:

POST /auth/register


Purpose:

Create a new user, hash the password, save the user, create JWT, and return the authenticated user response.


Request:

{
  "name": "Akhil",
  "email": "akhil@example.com",
  "password": "StrongPassword123",
  "role": "STUDENT"
}


Role behavior for V1:

Allow:

TRAINER
STUDENT

Both roles can register.

Both roles have the same permissions for workout/template functionality for now.

Role-based restrictions can be added later.


Recommended validation:

name:
- required
- not blank
- reasonable maximum length

email:
- required
- valid email format
- unique

password:
- required
- minimum 8 characters

role:
- required
- TRAINER or STUDENT


Example DTO:

@Data
public class RegisterRequest {

    @NotBlank
    private String name;

    @Email
    @NotBlank
    private String email;

    @NotBlank
    @Size(min = 8)
    private String password;

    @NotNull
    private Role role;
}


Registration logic:

1. Normalize email.
2. Check whether email already exists.
3. If yes, return HTTP 409 Conflict.
4. BCrypt-hash password.
5. Create User.
6. Save user.
7. Generate JWT.
8. Return AuthResponse.


Success response:

HTTP 201 Created

{
  "accessToken": "eyJhbGciOi...",
  "tokenType": "Bearer",
  "expiresIn": 86400,
  "user": {
    "id": 7,
    "name": "Akhil",
    "email": "akhil@example.com",
    "role": "STUDENT"
  }
}


The registration response should automatically authenticate the new user.

The frontend should not need to call /auth/login immediately after successful registration.


============================================================
9. LOGIN API
============================================================

Endpoint:

POST /auth/login


Request:

{
  "email": "akhil@example.com",
  "password": "StrongPassword123"
}


DTO:

@Data
public class LoginRequest {

    @Email
    @NotBlank
    private String email;

    @NotBlank
    private String password;
}


Login flow:

1. Normalize email.
2. Authenticate using AuthenticationManager.
3. Use email + password.
4. Spring Security verifies the BCrypt password.
5. Load User.
6. Generate JWT.
7. Return AuthResponse.


Success response:

HTTP 200 OK

{
  "accessToken": "eyJhbGciOi...",
  "tokenType": "Bearer",
  "expiresIn": 86400,
  "user": {
    "id": 7,
    "name": "Akhil",
    "email": "akhil@example.com",
    "role": "STUDENT"
  }
}


Invalid credentials response:

HTTP 401 Unauthorized

{
  "timestamp": "2026-09-10T19:30:00",
  "status": 401,
  "error": "Unauthorized",
  "message": "Invalid email or password",
  "path": "/auth/login"
}


Do NOT reveal whether the email or password was specifically incorrect.

Use:

"Invalid email or password"

instead of:

"User not found"

or:

"Wrong password"

No token / invalid token:

HTTP 401 Unauthorized


============================================================
11. LOGOUT
============================================================

No backend logout endpoint is required in V1.

JWT authentication is stateless.

Frontend logout:

1. Remove JWT access token.
2. Remove cached authenticated user.
3. Navigate to Login screen.


Do NOT create unnecessary token blacklist infrastructure in V1.

13. JWT CONTENT
============================================================

Recommended JWT claims:

subject:
- user's email

Additional claims:
- userId
- role


Conceptual JWT payload:

{
  "sub": "akhil@example.com",
  "userId": 7,
  "role": "STUDENT",
  "iat": ...,
  "exp": ...
}


Do NOT put sensitive information in JWT.

Do NOT put:
- password
- password hash
- reset token
- private user data


============================================================
14. JWT EXPIRATION
============================================================

For V1, use a reasonably long-lived access token.

Example:

24 hours


Configuration example:

app.jwt.expiration-ms=86400000


AuthResponse.expiresIn should be in seconds:

86400


Since there is no refresh token in V1:

When JWT expires:
- API returns 401
- frontend clears authentication
- user logs in again


============================================================
15. JWT SECRET
============================================================

Do NOT hardcode JWT secret in Java source code.

Use environment configuration.


Example:

app.jwt.secret=${JWT_SECRET}


Local development:

JWT_SECRET=<secure-random-secret>


Production:

Set JWT_SECRET as an environment variable in Render or hosting environment.


Secret must be sufficiently long and random.

============================================================
18. JWT AUTHENTICATION FILTER
============================================================

Create:

JwtAuthenticationFilter extends OncePerRequestFilter


Flow:

1. Read Authorization header.
2. If header missing -> continue filter chain.
3. If header does not start with "Bearer " -> continue.
4. Extract token.
5. Extract email from JWT.
6. If authentication is not already present:
   - load UserDetails
   - validate token
   - create UsernamePasswordAuthenticationToken
   - set authentication in SecurityContextHolder
7. Continue filter chain.


Important:

Invalid or expired JWT must NOT authenticate the request.

32. GETTING THE AUTHENTICATED USER IN SERVICES
============================================================

Avoid repeatedly parsing JWT manually inside controllers/services.

JWT filter should already populate Spring SecurityContext.


Possible approach:

Authentication authentication =
    SecurityContextHolder.getContext().getAuthentication();

String email = authentication.getName();

User currentUser = userRepository.findByEmail(email)
    .orElseThrow(...);


Better:

Create reusable helper/service such as:

CurrentUserService


Example:

public User getCurrentUser() {
    Authentication authentication =
        SecurityContextHolder.getContext().getAuthentication();

    String email = authentication.getName();

    return userRepository.findByEmail(email)
        .orElseThrow(() -> new RuntimeException("Authenticated user not found"));
}


Then existing services can use:

User currentUser = currentUserService.getCurrentUser();


This avoids repeating authentication extraction everywhere.


============================================================
33. DATABASE MIGRATION
============================================================

Existing users may not have passwords.

During development, plan migration carefully.


Add password column.

Example development SQL:

ALTER TABLE users ADD COLUMN password VARCHAR(255);


If making password NOT NULL immediately, existing rows will fail unless passwords are populated.

Development options:

Option A:
- recreate development users

Option B:
- add nullable password first
- update existing users with BCrypt hashes
- then set NOT NULL


Preferred for local MVP:

Recreate or update test users.


Do NOT insert raw passwords into password column.

Use BCrypt hashes.

============================================================

38. AXIOS 401 HANDLING
============================================================

Since V1 has no refresh token:

When backend returns 401:

1. Clear access token.
2. Clear authenticated user.
3. Redirect to login.


Avoid infinite redirect/interceptor loops.


Do not automatically retry with refresh token because refresh tokens are explicitly out of scope for V1.

47. SECURITY PRINCIPLES
============================================================

Always follow these rules:

- Never store plain passwords.
- Never return password hashes.
- Never trust userId from frontend for authenticated-user actions.
- Never hardcode JWT secrets.
- Never put secrets into JWT claims.
- Validate session/exercise log ownership.
- Use HTTPS in production.
- Normalize email addresses.
- Return generic invalid-login errors.
- Keep JWT logic centralized.
- Keep auth logic out of controllers where possible.
